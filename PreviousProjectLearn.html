1. RabbitMQ: send work between services

RabbitMQ is a message broker. A producer sends a message; RabbitMQ routes it to a queue; a consumer reads and handles it. The sender and receiver do not need to run at the same time.

Producer
sends message
→
Exchange
routes message
→
Queue
holds message
→
Consumer
handles work

Retry a failed message after a delay. If it keeps failing, send it to a dead-letter queue (DLQ) for investigation rather than retrying forever.

docker run -d --name rabbitmq -p 5672:5672 -p 15672:15672 rabbitmq:management

Think of the queue as a mailbox: the sender drops off a message and the receiver picks it up.

3. JUnit and Mockito

JUnit runs tests. Mockito creates substitute objects so a test can focus on one class without calling real databases or remote services.

class OrderServiceTest {
  @Mock PaymentClient paymentClient;
  @InjectMocks OrderService orderService;

  @Test void createsOrderWhenPaymentSucceeds() {
    when(paymentClient.charge(any())).thenReturn(true);
    var result = orderService.createOrder(new OrderRequest());
    assertTrue(result.isCreated());
  }
}
  • @Mock creates a fake dependency.
  • @InjectMocks creates the class under test and injects its mocks.
  • @Spy wraps a real object while letting you stub or verify selected calls. Prefer a mock when practical.

Test observable behavior through public methods instead of making tests depend on private implementation details.

4. Pact: check that two services agree

Pact is a contract-testing tool for a service that calls an API (consumer) and the service that provides it (provider).

Consumer test
records expectation
→
Pact file
the contract
→
Provider verify
checks API behavior
  1. Write a consumer test describing the request and expected response.
  2. Publish the generated contract to a Pact Broker.
  3. Run provider verification against the provider implementation.
  4. Publish verification results so deployment pipelines can check compatibility.

Version and branch tags identify builds. Keep broker credentials and private URLs in secure configuration.

6. Spring WebClient: call another HTTP service

This example sends JSON and reads a successful response as Result.

Result result = webClient.post()
    .uri("/orders")
    .contentType(MediaType.APPLICATION_JSON)
    .accept(MediaType.APPLICATION_JSON)
    .bodyValue(orderRequest)
    .retrieve()
    .onStatus(HttpStatusCode::isError, response ->
        response.bodyToMono(String.class)
            .map(body -> new OrderServiceException(body)))
    .bodyToMono(Result.class)
    .block();

post() chooses the method; uri() chooses the path; contentType describes the request body; accept describes the desired response; bodyValue supplies request data. retrieve() sends the request and bodyToMono describes response conversion.

block() waits synchronously. It may suit a synchronous application, but avoid blocking inside a reactive request flow; return and compose the Mono instead.

7. JWT and an API gateway

A JWT is a compact token containing claims such as a user ID or expiry. A signed JWT lets a receiver detect changes; signing does not hide the token's contents.

Client
sends token
→
API gateway
checks token
→
Backend API
checks access

An API gateway such as Apigee can validate a token, apply policies, and route accepted requests to a backend. Authentication asks “Who are you?” Authorization asks “May you do this?”

Interview answer: “The issuer signs the JWT. The gateway or service validates its signature and expiry, then checks permissions before allowing access.”

Invalid or missing authentication commonly maps to 401; a valid identity without permission commonly maps to 403. API designs can differ.

9. Symmetric and asymmetric keys

TypeHow it worksTrade-off
SymmetricThe same secret key encrypts and decrypts.Fast; parties must securely share and protect the secret.
AsymmetricPublic/private key pair; signing and verification use matching keys.Helps establish trust; involves more computation and key management.

For a signed JWT, the issuer signs with a private key and the receiver verifies with the matching public key. This proves the token was not changed and was signed by the private-key holder. It does not encrypt the token.

“More secure” depends on purpose and key handling; the two methods solve different problems.

10. Flyway database migrations

Flyway applies versioned SQL changes in order and records which ones have run, helping environments reach a consistent database structure.

CommandPurpose
migrateApply pending migrations.
infoShow migration status.
validateCheck migration files against recorded checksums.
baselineMark an existing database as a starting point.
repairRepair history metadata after diagnosis; it does not fix a broken schema.
cleanDrop database objects in configured schemas.
undoUndo only when the edition and migration setup support it.

clean is destructive. Never run it on a shared or production database unless that is explicitly intended and understood.

11. Cron expressions and scheduled jobs

The notes use a six-field Spring-style expression:

second  minute  hour  day-of-month  month  day-of-week
0       0       2     *             *      *

0 0 2 * * * means “run at 2:00 AM every day” in Spring's six-field format. Common symbols: * every value; ? no specific day value in schedulers that support it; , list; - range; / step. Traditional Unix cron usually has five fields; Quartz has its own rules.

For cleanup jobs, check time zone, retention rules, batch size, and whether rerunning the job is safe.

13. Configuration and deployment

Applications combine defaults with environment-specific settings. Exact precedence depends on framework and setup; in Spring Boot, command-line arguments and environment variables commonly override packaged config. Confirm property sources for your app.

ConfigMaps hold non-secret settings. Secrets are for sensitive values, but access must still be controlled. Never put credentials in source code, images, logs, or shared notes.

oc project <project-name>
oc get pods
oc get deployments
oc describe pod <pod-name>
oc logs <pod-name>

These commands inspect the selected project, pods, deployment details, and logs. Replace placeholders with authorized project and pod names.
