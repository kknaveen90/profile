All 59 questions, in simpler words. Read the short answer first. Use the example and diagram to understand why it is true. Read code only after the steps make sense. Question labels match the original PDFs: A1-A24, B1-B20 and C1-C15.

First: a few useful words

Thread: One worker running instructions inside your application.

Shared data: A value or object that more than one thread can use.

Atomic: The operation acts as one indivisible step to other threads.

Lock: A way to let only one cooperating thread enter protected work at a time.

HashMap bucket: One place inside the map where entries are stored.

Future: An object representing a result that may be available later.

Transaction: Related database changes handled as one unit: they commit together or are rolled back.

Proxy: A wrapper around an object that can add work before or after a method call.

Stream pipeline: A source plus processing steps, ending in an operation that runs the work.

Terminal operation: The final stream operation, such as count() or collect(), that triggers evaluation.

Comparator: A rule that tells Java which of two values should come first.

Optional: A result container that may hold one answer or may be empty.

groupingBy / counting: Put equal keys in groups / count the elements in each group.

Function.identity(): Use the input value itself, without changing it.

Complexity: How the amount of work or memory grows when the input grows.

Three concurrency ideas

Atomicity: one complete action

Think of updating a counter. count++ reads a number, adds one, then writes it back. Two threads can overlap these steps and lose an update. AtomicInteger makes its increment act as one step.

SAY THISAtomicity means another thread cannot interfere in the middle of this operation.

Visibility: seeing another thread's update

Thread A changes a shared running flag to false. Thread B needs to observe that change so it can stop its loop. volatile provides visibility guarantees when threads write and read that field.

SAY THISVisibility means one thread can see the updates made by another thread.

Ordering: seeing the right sequence

Thread A writes data = 42, then sets a volatile ready flag to true. If thread B reads that true value, the earlier data write is visible too. Assume no other thread changes these values.

SAY THISOrdering means Java gives rules about which earlier actions must be visible after a later signal.

A. Senior Java questions

A1. HashMap collisions and treeification

SAY THIS TO THE INTERVIEWERWhen two keys go to the same HashMap bucket, Java checks equals() to tell them apart. Different keys can stay in the same bucket. If too many entries collect there, Java can change the list into a tree to help with searching.

Understand with an example: Think of a bucket as a shelf. Two books can be on the same shelf, but their titles tell you which book you want. The hash helps choose the shelf; equals() helps choose the key.

Remember: If asked about numbers: OpenJDK uses a threshold of 8 and needs at least 64 table slots. In the usual put path, adding the ninth colliding entry triggers the tree change. A smaller table grows first.

A2. Can a concurrent HashMap operation loop forever?

SAY THIS TO THE INTERVIEWERHashMap is not safe when threads change it at the same time without coordination. Older Java versions could even create a loop inside a bucket during resizing. I would use ConcurrentHashMap for a shared map with concurrent updates.

Understand with an example: Two people rearranging the same chain at once can connect its links incorrectly. In the old bug, following the links could keep bringing you back to an earlier link.

Remember: The famous infinite-loop explanation mainly concerns old Java 7 resize behavior. Do not claim that every modern HashMap has that same bug.

A3. Same hashCode, different keys?

SAY THIS TO THE INTERVIEWERYes. Two keys can have the same hashCode and still be different. HashMap uses equals() to decide whether they are the same key. If equals() is false, both can be stored.

Understand with an example: The strings "FB" and "Ea" have the same hash code, but they are different strings. Putting both into a HashMap gives two entries.

Remember: Same hash does not mean same key. If equals() is true, their hash codes must also be equal.

A4. Can static methods be overridden?

SAY THIS TO THE INTERVIEWERNo, static methods are hidden, not overridden. Java chooses a static method using the reference type at compile time. For an overridden instance method, Java uses the actual object type at runtime.

Understand with an example: If Parent p = new Child(), p.staticMethod() chooses the Parent static method. But p.instanceMethod() chooses the Child override, if Child provides one.

Remember: Call static methods using the class name, such as Parent.staticMethod(), to make the choice clear.

A5. Why compile-time overloading but runtime overriding?

SAY THIS TO THE INTERVIEWEROverloading means choosing between methods with different parameters. Java makes that choice while compiling. Overriding means choosing a subclass implementation of the chosen method, and Java makes that choice while running.

Understand with an example: Suppose print(Object) and print(String) both exist. With Object value = "hello", print(value) chooses print(Object), because the variable is declared as Object.

Remember: First Java chooses the method signature. Then, for an instance call, it can choose an override of that same signature.

A6. Constructor calling an overridable method

SAY THIS TO THE INTERVIEWERA constructor can call a subclass method before the subclass is fully initialized. That method may see null or zero instead of the expected values. I avoid calling overridable methods from constructors.

Understand with an example: The parent constructor calls show(). Java runs Child.show(), but the child name field has not yet been set to "ready". The method sees null.

Remember: Use a private or final helper for constructor work. A final method cannot be replaced by a subclass override.

A7. Immutable class containing a mutable object

SAY THIS TO THE INTERVIEWERYes. An immutable class can contain a mutable object if it keeps its own copy and does not expose that object directly. I copy mutable values on input and return a copy when needed.

Understand with an example: If I store a caller's Date directly, the caller can change it later. Copying the Date in the constructor stops that outside change from changing my object.

Remember: final prevents assigning a new object to the field. It does not stop changes inside the existing object. Prefer immutable values such as Instant when possible.

A8. Two threads update the same ConcurrentHashMap key

SAY THIS TO THE INTERVIEWERConcurrentHashMap safely handles simultaneous updates. If two threads put different values for the same key, one update comes after the other and its value remains. For a counter, I use merge() or compute() so reading and updating happen as one map operation.

Understand with an example: Two threads adding 1 with separate get() and put() calls can both read 0 and both write 1. merge("java", 1, Integer::sum) avoids that lost increment.

Remember: A safe map does not make a separate get-then-put sequence atomic. It also does not make a mutable object stored inside it safe.

A9. volatile vs AtomicInteger; is count++ safe?

SAY THIS TO THE INTERVIEWERvolatile helps threads see updates, but it does not make count++ a single operation. Two threads can still lose an increment. AtomicInteger.incrementAndGet() makes that increment atomic.

Understand with an example: Start with count = 0. Thread A reads 0 and thread B also reads 0. Each adds 1 and writes 1. The result is 1, even though two increments happened.

Remember: Say: volatile is useful for a shared flag; AtomicInteger is useful for a shared counter. Use a lock when several values must change together.

A10. Deadlock despite synchronized blocks

SAY THIS TO THE INTERVIEWERDeadlock happens when threads wait for each other forever. synchronized protects a lock, but it does not stop threads from taking different locks in the wrong order. I use a consistent lock order and check thread dumps to find the waiting cycle.

Understand with an example: Thread 1 holds lock A and wants lock B. Thread 2 holds lock B and wants lock A. Neither can move forward.

Remember: Make both threads take A before B. A thread dump shows which thread holds each lock and which lock it is waiting for.

A11. thenApply throws: how to recover?

SAY THIS TO THE INTERVIEWERIf thenApply() throws, that future ends with an error and later success steps are skipped. I can use exceptionally() to return a fallback value, so the next steps can continue. handle() can deal with both success and failure.

Understand with an example: Parsing "bad" as an integer fails. exceptionally(error -> 0) gives 0 instead. A following step that adds 1 can then produce 1.

Remember: whenComplete() is mainly for observing the result, such as logging. It does not normally turn a failure into a success.

A12. thenApply vs thenCompose vs thenCombine

SAY THIS TO THE INTERVIEWERI use thenApply() to turn a result into another value. I use thenCompose() when the next task depends on that result and returns another future. I use thenCombine() to combine two separate task results.

Understand with an example: Get a user name from a user: thenApply. Fetch orders after getting the user ID: thenCompose. Combine a user result and a price result: thenCombine.

Remember: A future represents a result that may arrive later. thenCompose avoids a future wrapped inside another future.

A13. 200 threads but 10 database connections

SAY THIS TO THE INTERVIEWEROnly ten tasks can hold database connections at once. Many other threads may wait and eventually time out. I would check slow queries, long transactions, connection leaks, and pool metrics, then limit the work reaching the database.

Understand with an example: Think of 200 customers and ten service counters. Adding more customers does not create more counters. Long service times make the queue grow.

Remember: Do not immediately increase the connection pool to 200. The database may become slower under that load.

A14. Thread-pool exhaustion with low CPU

SAY THIS TO THE INTERVIEWERYes. A thread pool can be full even when CPU usage is low. Its workers may be waiting for a database, a network call, or a lock. I would inspect their thread dumps and the task queue to find what they are waiting for.

Understand with an example: All ten workers are waiting for slow API responses. New tasks stay in the queue, even though the CPU has little work to do.

Remember: Also check whether workers are waiting for child tasks submitted to the same full pool. Use timeouts and avoid such waiting cycles.

A15. Investigating BLOCKED and WAITING threads

SAY THIS TO THE INTERVIEWERI take several thread dumps and compare them. I look at what threads are waiting for and who holds the locks. I also check database connections and request latency before deciding whether the waiting is a problem.

Understand with an example: BLOCKED usually means waiting to enter a synchronized block. WAITING can mean waiting for a task, signal, or another thread. An idle worker waiting for a task is normal.

Remember: One snapshot is not enough. Repeatedly seeing the same busy request stuck on the same dependency is more useful evidence.

A16. Why parallel streams may be slower

SAY THIS TO THE INTERVIEWERA parallel stream has extra work: splitting data, running tasks, and joining results. For small lists or simple operations, that extra work can cost more than it saves. I would measure it before choosing parallel processing.

Understand with an example: Asking four people to add five numbers needs coordination. One person could finish sooner. Parallel work helps more when there is enough independent work to share.

Remember: Blocking calls, shared data changes, and order requirements can also make parallel streams slower.

A17. Modifying a collection during stream processing

SAY THIS TO THE INTERVIEWERI avoid changing the source collection while its stream is running. With a normal list, that can cause ConcurrentModificationException or incorrect results. I usually create a new filtered list instead.

Understand with an example: While reading a list of employees, removing employees from that same list changes what is being read. Filtering into a new list avoids this problem.

Remember: The exception is not guaranteed every time. Not seeing an exception does not make the change safe.

A18. Reusing a stream after a terminal operation

SAY THIS TO THE INTERVIEWERNo. A stream is used only once. After a terminal operation such as count() or collect(), I create a fresh stream for another operation. Reusing the old stream can throw IllegalStateException.

Understand with an example: I can call employees.stream().count(), then employees.stream().toList(). These use two new streams over the same list.

Remember: The list can be read again. The already-used stream cannot be used again.

A19. StackOverflowError vs OutOfMemoryError

SAY THIS TO THE INTERVIEWERStackOverflowError usually happens when method calls become too deep, often because of endless recursion. OutOfMemoryError means Java cannot get memory or another required resource. I investigate the exact error message because the fixes are different.

Understand with an example: A method calling itself forever can overflow its stack. Keeping millions of large objects alive can fill the heap and cause an out-of-memory error.

Remember: More heap memory does not fix endless recursion. OutOfMemoryError can also involve memory outside the heap.

A20. Self-invocation between @Transactional methods

SAY THIS TO THE INTERVIEWERIn normal Spring proxy mode, a method calling another method in the same object bypasses the transaction proxy. The second method's transaction settings are not applied separately. It can still run in a transaction that the first method already started.

Understand with an example: outer() already has a transaction and calls this.inner(). Even if inner() says REQUIRES_NEW, that direct call does not start the requested new transaction.

Remember: A proxy is a wrapper that starts transaction work before calling the real method. Move the second operation to another injected service when it needs its own transaction boundary.

A21. Why @Transactional on a private method fails

SAY THIS TO THE INTERVIEWERIn normal proxy mode, Spring cannot intercept a private method through the proxy. So @Transactional on that private method does not start a transaction by itself. I put the transaction on a suitable service method called from outside the object.

Understand with an example: A public service method can start a transaction, and its private helper can use that transaction. The helper's own annotation is not what started it.

Remember: Private methods are the issue here. Some non-public methods are supported by class-based proxies in newer Spring versions.

A22. Circular dependencies between Spring beans

SAY THIS TO THE INTERVIEWERA circular dependency means bean A needs bean B, while B also needs A. With constructor injection, Spring cannot normally create either one first. I would change the design, often by moving shared work into a third service.

Understand with an example: OrderService needs PaymentService to be created. PaymentService also needs OrderService. Each is waiting for the other object.

Remember: @Lazy can delay getting a dependency, but it can hide the design issue. Prefer breaking the cycle.

A23. Fixing Hibernate N+1 without blanket EAGER

SAY THIS TO THE INTERVIEWERN+1 means one query loads the main records, then extra queries load related data one record at a time. I would fetch the needed data for that use case with a fetch join, an entity graph, or a DTO query. I would check the generated SQL to confirm the fix.

Understand with an example: One query loads ten departments. Reading employees for each department triggers ten more queries. That makes eleven queries instead of the intended smaller number.

Remember: Making every relationship EAGER may fetch too much and still may not produce one query. Be careful with collection fetch joins and pagination.

A24. DB commit succeeds, crash before Kafka publish

SAY THIS TO THE INTERVIEWERThe database change can be saved while the Kafka event is lost. I would use the transactional outbox pattern: save the business change and an event record in one database transaction. A separate publisher sends the saved event and retries after failures.

Understand with an example: When saving an order, also save an "OrderCreated" outbox row. If the application crashes, that row is still there, so the publisher can send the event later.

Remember: The same event may be sent again during retries. Give it an event ID so consumers can avoid processing it twice.

B. Streams coding questions

B1. Find the second-highest salary

SAY THIS TO THE INTERVIEWERI would first ask whether repeated salaries count as separate positions. For the second distinct salary, I remove duplicates, sort from highest to lowest, skip one, and take the next value.

Understand with an example: For salaries 90, 90, 70, 50, the second distinct salary is 70. If we counted employee positions instead, the second position could still be 90.

Remember: findFirst() returns Optional.empty() if there is no second distinct salary. Optional means the answer may be missing.

Code - open after you understand the steps
Optional<Long> second = employees.stream()
    .map(Employee::salary).distinct()
    .sorted(Comparator.reverseOrder())
    .skip(1).findFirst();

If asked about performance: O(n + d log d) time, O(d) auxiliary storage, where d is the number of distinct salaries. A two-best scan can do O(n) time and O(1) extra space.

B2. Find the highest salary in each department

SAY THIS TO THE INTERVIEWERI group employees by department, then find the employee with the highest salary in each group. groupingBy() makes the groups and maxBy() selects the highest-paid employee.

Understand with an example: IT has salaries 90 and 70; HR has 80 and 60. The result keeps the employee earning 90 in IT and the employee earning 80 in HR.

Remember: If several employees tie, ask whether the interviewer wants one employee or everyone with the highest salary.

Code - open after you understand the steps
Map<String, Optional<Employee>> best = employees.stream()
    .collect(groupingBy(Employee::department,
      maxBy(Comparator.comparingLong(Employee::salary))));

If asked about performance: O(n) expected time; O(g) aggregation storage for g departments.

B3. Find duplicate elements in a list

SAY THIS TO THE INTERVIEWERI count how many times each value appears, then keep values whose count is more than one. This returns each duplicated value once.

Understand with an example: For [a, b, a, c, b], the counts are a=2, b=2, c=1. So the duplicate values are a and b.

Remember: LinkedHashMap preserves first appearance order. A normal HashMap does not promise that order.

Code - open after you understand the steps
Map<String, Long> counts = words.stream().collect(
    groupingBy(Function.identity(), LinkedHashMap::new,
      counting()));
List<String> duplicates = counts.entrySet().stream()
    .filter(e -> e.getValue() > 1)
    .map(Map.Entry::getKey).toList();

If asked about performance: O(n) expected time and O(d) counting storage.

B4. Find the first non-repeated character

SAY THIS TO THE INTERVIEWERI count each character, keeping the order in which characters first appear. Then I take the first character with a count of one.

Understand with an example: In "swiss", s appears three times. Both w and i appear once, but w comes first. So the answer is w.

Remember: Keep the original order. The simple character examples here use ordinary English text; full Unicode handling needs code points.

Code - open after you understand the steps
Map<Integer, Long> freq = text.codePoints().boxed()
    .collect(groupingBy(Function.identity(),
      LinkedHashMap::new, counting()));
Optional<String> first = freq.entrySet().stream()
    .filter(e -> e.getValue() == 1)
    .map(e -> new String(Character.toChars(e.getKey())))
    .findFirst();

If asked about performance: O(n) expected time and O(d) storage for distinct code points.

B5. Count character frequency

SAY THIS TO THE INTERVIEWERI group the same characters together and count how many times each appears. groupingBy() chooses the character as the key and counting() gives its frequency.

Understand with an example: In "banana", b appears once, a appears three times, and n appears twice.

Remember: Decide whether uppercase and lowercase should count as different characters. Spaces also count unless you remove them.

Code - open after you understand the steps
Map<Integer, Long> frequency = text.codePoints().boxed()
    .collect(groupingBy(Function.identity(),
      LinkedHashMap::new, counting()));

If asked about performance: O(n) expected time, O(d) storage.

B6. Count word frequency

SAY THIS TO THE INTERVIEWERI turn the sentence into words, normalize case if needed, and count each word. I also define how punctuation should be handled.

Understand with an example: For "Java java, streams!", after making case and punctuation consistent, the counts are java=2 and streams=1.

Remember: Tokenizing means splitting text into words. Different languages and punctuation may need different splitting rules.

Code - open after you understand the steps
Map<String, Long> frequency = Arrays.stream(
    sentence.toLowerCase(Locale.ROOT)
      .split("[^\\p{L}\\p{N}]+"))
    .filter(s -> !s.isEmpty())
    .collect(groupingBy(Function.identity(), counting()));

If asked about performance: Expected O(L) counting/tokenization for input length L, excluding language-dependent normalization details.

B7. Find the first repeated character

SAY THIS TO THE INTERVIEWERI scan from left to right and remember the characters I have seen. The first character already in that set is the first repeated character. A loop is a clear way to write this.

Understand with an example: For "abccba", I see a, b, and c for the first time. The next c has already been seen, so c is the answer.

Remember: Ask what "first repeated" means. Here it means the first second-occurrence encountered, not the earliest original character that repeats later.

Code - open after you understand the steps
static Optional<String> firstRepeated(String text) {
  Set<Integer> seen = new HashSet<>();
  PrimitiveIterator.OfInt it = text.codePoints().iterator();
  while (it.hasNext()) {
    int cp = it.nextInt();
    if (!seen.add(cp))
      return Optional.of(
        new String(Character.toChars(cp)));
  }
  return Optional.empty();
}

If asked about performance: O(n) expected time, O(d) space; stops at the first repeat.

B8. Employees earning above average salary

SAY THIS TO THE INTERVIEWERI calculate the average salary first. Then I use a new stream to keep employees earning more than that average.

Understand with an example: For salaries 50, 70, and 90, the average is 70. Only the employee earning 90 is above average.

Remember: An empty employee list has no average. Return an empty result instead of assuming a real average exists.

Code - open after you understand the steps
OptionalDouble average = employees.stream()
    .mapToLong(Employee::salary).average();
List<Employee> above = average.isEmpty() ? List.of()
    : employees.stream()
        .filter(e -> e.salary() > average.getAsDouble())
        .toList();

If asked about performance: O(n) time with two passes; O(k) result storage.

B9. Group employees by department

SAY THIS TO THE INTERVIEWERI use groupingBy() with the employee's department. The result is a map where each department points to its employees.

Understand with an example: Alice and Bob work in IT; Carol works in HR. The result is IT -> [Alice, Bob] and HR -> [Carol].

Remember: Grouping organizes the existing employee objects. It does not make copies of those objects.

Code - open after you understand the steps
Map<String, List<Employee>> groups = employees.stream()
    .collect(groupingBy(Employee::department,
      LinkedHashMap::new, toList()));

If asked about performance: O(n) expected time and O(n + g) result storage.

B10. Sort employees by salary

SAY THIS TO THE INTERVIEWERI use sorted() with a salary comparator. reversed() makes the highest salary come first. I can add a name comparison to make tied salaries predictable.

Understand with an example: Employees earning 50, 90, and 70 become 90, 70, and 50. The original employee list is not sorted in place by this stream.

Remember: A comparator tells Java which of two values should come first. Do not subtract large salaries in a comparator because the result can overflow.

Code - open after you understand the steps
List<Employee> sorted = employees.stream()
    .sorted(Comparator.comparingLong(Employee::salary)
      .reversed().thenComparing(Employee::name))
    .toList();

If asked about performance: O(n log n) time and O(n) result/buffering space.

B11. Find maximum and minimum elements

SAY THIS TO THE INTERVIEWERI can use min() and max() on separate fresh streams. If I want both in one pass, summaryStatistics() is convenient. I check whether the input is empty before using the results.

Understand with an example: For [4, 1, 9], the minimum is 1 and the maximum is 9.

Remember: A statistics object also gives count, sum, and average. Its empty min/max values are placeholders, not real input values.

Code - open after you understand the steps
IntSummaryStatistics stats = numbers.stream()
    .mapToInt(Integer::intValue).summaryStatistics();
if (stats.getCount() > 0) {
  System.out.println(stats.getMin());
  System.out.println(stats.getMax());
}

If asked about performance: O(n) time, O(1) summary state.

B12. Find the top three highest salaries

SAY THIS TO THE INTERVIEWERFor the top three different salary amounts, I remove duplicates, sort highest first, and use limit(3). If the question asks for three employees, I sort employees instead.

Understand with an example: For 90, 90, 70, 60, 50, the top three different amounts are 90, 70, and 60.

Remember: Sorting still needs to read all the unsorted input. limit(3) after sorted() does not avoid that work.

Code - open after you understand the steps
List<Long> top = employees.stream()
    .map(Employee::salary).distinct()
    .sorted(Comparator.reverseOrder())
    .limit(3).toList();

If asked about performance: O(n + d log d) time, O(d) buffering. A bounded heap can reduce work for small k.

B13. Find the Nth highest salary

SAY THIS TO THE INTERVIEWERI remove duplicate salaries, sort highest first, skip N minus one values, and take the next value. I check that N is at least one.

Understand with an example: For 90, 70, 60, 50 and N=3, I skip 90 and 70. The answer is 60.

Remember: If there are not enough different salaries, the result is empty. Always clarify whether duplicates should count toward the rank.

Code - open after you understand the steps
if (rank < 1)
  throw new IllegalArgumentException("rank must be >= 1");
Optional<Long> nth = employees.stream()
    .map(Employee::salary).distinct()
    .sorted(Comparator.reverseOrder())
    .skip(rank - 1L).findFirst();

If asked about performance: O(n + d log d) time, O(d) storage.

B14. Partition numbers into even and odd

SAY THIS TO THE INTERVIEWERI use partitioningBy() with the condition number % 2 == 0. The true group contains even numbers and the false group contains odd numbers.

Understand with an example: For [1, 2, 3, 4], true contains [2, 4] and false contains [1, 3].

Remember: Both groups exist, even if one is empty. For checking odd numbers, use % 2 != 0 so negative odd numbers also work.

Code - open after you understand the steps
Map<Boolean, List<Integer>> parts = numbers.stream()
    .collect(partitioningBy(n -> n % 2 == 0));

If asked about performance: O(n) time, O(n) output storage.

B15. Calculate salary sum and average

SAY THIS TO THE INTERVIEWERI convert the salaries to a number stream and use summaryStatistics(). It gives me the total, average, and count in one pass.

Understand with an example: Salaries 50, 70, and 90 add up to 210. Dividing by three gives an average of 70.

Remember: For money, choose a clear unit and rounding rule. These examples use whole-number minor units such as cents.

Code - open after you understand the steps
LongSummaryStatistics stats = employees.stream()
    .mapToLong(Employee::salary).summaryStatistics();
long sum = stats.getSum();
double avg = stats.getAverage();

If asked about performance: O(n) time, O(1) summary state.

B16. Convert List<Employee> to Map<Id, Employee>

SAY THIS TO THE INTERVIEWERI use toMap() with employee ID as the key and the employee as the value. I decide what should happen if the same ID appears twice. By default, duplicate keys cause an exception.

Understand with an example: Employee 1 is Alice and employee 2 is Bob. The result is 1 -> Alice's employee object and 2 -> Bob's employee object.

Remember: The example rejects duplicate IDs. Do not silently keep the first or last record unless that is the required rule.

Code - open after you understand the steps
Map<Long, Employee> byId = employees.stream().collect(
    toMap(Employee::id, Function.identity(),
      (a, b) -> {
        throw new IllegalArgumentException("duplicate id");
      }, LinkedHashMap::new));

If asked about performance: O(n) expected time, O(n) output storage.

B17. Employees whose names start with a given character

SAY THIS TO THE INTERVIEWERI use filter() to keep employees whose names start with the given prefix. startsWith() checks the beginning of each name.

Understand with an example: With prefix "A", Alice and Arun match. Bob does not match.

Remember: startsWith() is case-sensitive: "Alice" matches "A", but "alice" does not. The example assumes names are not null.

Code - open after you understand the steps
String prefix = "A";
List<Employee> matches = employees.stream()
    .filter(e -> e.name().startsWith(prefix))
    .toList();

If asked about performance: O(n * p) worst-case prefix comparisons for prefix length p; O(k) output.

B18. Find the longest string

SAY THIS TO THE INTERVIEWERI use max() with a comparator based on string length. That returns the longest string, or an empty Optional if the list has no strings.

Understand with an example: For [cat, elephant, dog], elephant has the greatest length, so it is the answer.

Remember: If strings tie in length, decide whether any longest string is acceptable or whether you need a tie-break rule.

Code - open after you understand the steps
Optional<String> longest = words.stream().max(
    Comparator.comparingInt((String s) ->
      s.codePointCount(0, s.length()))
      .thenComparing(Comparator.naturalOrder()));

If asked about performance: O(total compared text length) time for code-point counting; O(1) reduction state.

B19. Remove duplicates using Streams

SAY THIS TO THE INTERVIEWERI use distinct() to remove repeated values. For a list stream, it keeps the first occurrence of each equal value.

Understand with an example: [a, b, a, c, b] becomes [a, b, c].

Remember: For your own objects, equals() and hashCode() must describe equality correctly. Same employee ID may need a special rule.

Code - open after you understand the steps
List<String> unique = words.stream().distinct().toList();

If asked about performance: Typically O(n) expected time and O(d) distinct-state storage, plus the result.

B20. Find common elements between two lists

SAY THIS TO THE INTERVIEWERI put the second list into a Set, then filter the first list using that set. I add distinct() if each common value should appear only once.

Understand with an example: List A is [1, 2, 2, 3] and list B is [2, 3, 4]. The unique common values are [2, 3].

Remember: A Set makes repeated membership checks fast. Without distinct(), both copies of 2 from the first list would remain.

Code - open after you understand the steps
Set<Integer> lookup = new HashSet<>(right);
List<Integer> common = left.stream()
    .filter(lookup::contains).distinct().toList();

If asked about performance: O(n+m) expected time; O(m+d) lookup/deduplication storage.

C. Streams conceptual questions

C1. Stream vs Collection

SAY THIS TO THE INTERVIEWERA Collection stores data. A Stream processes data from a source, often a collection. I can read a collection again, but I use each stream only once.

Understand with an example: A list is like a box of apples. A stream is the process of selecting large apples and counting them. The process does not replace the box.

Remember: A stream does not automatically copy the data or make it safe for concurrent changes.

C2. Intermediate vs terminal operations

SAY THIS TO THE INTERVIEWERIntermediate operations build the processing steps and return another stream. Terminal operations run the pipeline and produce a result or action. filter() and map() are intermediate; collect() and count() are terminal.

Understand with an example: In employees.stream().filter(...).count(), filter describes which employees to keep. count triggers the work and gives the number.

Remember: Building a stream without a terminal operation normally does not process its elements.

C3. map vs flatMap

SAY THIS TO THE INTERVIEWERmap() changes each element into one result. flatMap() is useful when each element contains several values and I want one combined stream.

Understand with an example: With [[a, b], [c]], map can keep nested lists. flatMap(List::stream) gives a, b, c in one stream.

Remember: Think: map transforms; flatMap transforms and removes one level of nesting.

C4. filter vs map

SAY THIS TO THE INTERVIEWERfilter() decides which elements to keep. map() changes each kept element into a value. I often filter employees first, then map them to their names.

Understand with an example: From employees, filter keeps those earning more than 50,000. map(Employee::name) then returns just their names.

Remember: filter uses a true/false test. map returns the transformed value.

C5. map vs peek

SAY THIS TO THE INTERVIEWERmap() changes the values used by the next step. peek() observes values, usually for debugging, and passes the same values onward. I do not use peek() for required business updates.

Understand with an example: map(String::toUpperCase) produces uppercase strings. peek(System.out::println) prints what it sees but does not replace the string.

Remember: Some stream optimizations and early stopping can skip peek calls. Do not depend on it for saving data or auditing.

C6. findFirst vs findAny

SAY THIS TO THE INTERVIEWERfindFirst() returns the first value in the stream's order, when there is an order. findAny() may return any value. I use findAny() when I do not care which match I get.

Understand with an example: From an ordered stream of [10, 20, 30], findFirst gives 10. findAny is allowed to give any one of these values.

Remember: findAny does not mean random. Both methods return Optional because the stream might be empty.

C7. reduce vs collect

SAY THIS TO THE INTERVIEWERI use reduce() to combine values, such as adding numbers into one total. I use collect() to build a result container, such as a list, set, or map.

Understand with an example: Numbers 1, 2, 3 can be reduced to the sum 6. Employee names can be collected into a List<String>.

Remember: For parallel reduce, grouping calculations differently must still give the same result. Addition works; subtraction does not.

C8. groupingBy vs partitioningBy

SAY THIS TO THE INTERVIEWERgroupingBy() can create many groups, such as one per department. partitioningBy() creates two groups based on a true/false condition.

Understand with an example: groupingBy can produce IT, HR, and Sales. partitioningBy can split numbers into even and odd.

Remember: partitioningBy includes both true and false keys even when a group is empty.

C9. What is lazy evaluation?

SAY THIS TO THE INTERVIEWERLazy evaluation means stream steps wait until a terminal operation needs the result. Java then does the needed work, and some operations can stop early.

Understand with an example: filter(...).findFirst() can stop as soon as it finds a match. Without findFirst or another terminal operation, the filter normally does not run.

Remember: Some steps still need all the input. For example, sorting an unsorted stream usually needs to read everything first.

C10. Can a stream be reused?

SAY THIS TO THE INTERVIEWERNo. A stream can only be used once. I create a new stream each time I need another result from the same collection.

Understand with an example: Use numbers.stream().count() for the count, then a new numbers.stream() for the sum. Do not reuse the first stream object.

Remember: This is the same rule as A18. Reusing a consumed stream can throw IllegalStateException.

C11. Sequential vs parallel streams

SAY THIS TO THE INTERVIEWERA sequential stream processes work in sequence, normally on one thread. A parallel stream splits work across tasks and joins the results. Parallel can help with enough independent CPU work, but it is not always faster.

Understand with an example: A large set of expensive calculations may benefit from several workers. A small list of simple additions may finish faster sequentially.

Remember: Do not write to the same ordinary list from parallel stream steps. Use a suitable collector to build results.

C12. When to avoid parallelStream

SAY THIS TO THE INTERVIEWERI avoid parallelStream() for small tasks, blocking calls, or work that changes shared data. I also avoid it when keeping order or sharing worker threads creates too much overhead. I measure before using it.

Understand with an example: Calling a slow remote API for every element can keep stream workers waiting. Explicit concurrency with timeouts may be easier to control.

Remember: Parallel streams commonly share worker resources with other work. More tasks do not automatically mean more capacity.

C13. How distinct works

SAY THIS TO THE INTERVIEWERdistinct() remembers which values have already appeared and skips repeats. It uses equality rules to decide whether values are duplicates. On an ordered stream, the first occurrence is kept.

Understand with an example: For a, b, a: keep the first a, keep b, and skip the second a. The result is a, b.

Remember: This is the simple mental model; Java can optimize special sources. For custom objects, implement equals() and hashCode() correctly.

C14. How sorted works internally

SAY THIS TO THE INTERVIEWERsorted() puts elements in natural order or the order defined by a comparator. For a normal unsorted stream, Java usually gathers the elements before it can return sorted results.

Understand with an example: Input [3, 1, 2] must be read before Java can confidently emit [1, 2, 3]. If only 3 had been read, 1 could still appear later.

Remember: sorted().limit(3) normally still sorts the whole unsorted input. The exact sorting algorithm is an implementation detail.

C15. Exception handling in Streams

SAY THIS TO THE INTERVIEWERIf stream code throws an unchecked exception, the terminal operation normally fails. I decide whether the whole operation should fail or whether each item should carry its own success or error result.

Understand with an example: Parsing ["10", "bad", "20"] as integers fails at "bad". If the business needs the valid results too, I handle each parse failure explicitly instead of silently returning null.

Remember: A stream failure does not undo earlier changes. Checked exceptions must be handled or wrapped appropriately inside a lambda.

How to practice

Start with the answer. Say yes/no or state the main difference first. Add one reason and one example. Stop there unless the interviewer asks for more.

For coding questions. Explain the steps before writing the code: for example, remove duplicates, sort, skip one, take the next value.

Ask about unclear rules. For salary questions: distinct amounts or employee positions? For ties: one answer or all tied answers? For missing results: empty Optional or another policy?

Explain performance simply. O(n): visit each item once. O(n log n): typical sorting work. O(n*m): compare every item in one list with every item in another. Extra memory means temporary storage beyond the input.

Know the limits. Check empty inputs, null policy and duplicate IDs. These examples use Java 17+. Stream.toList() returns a list that cannot be changed through the returned list.

Practice aloud. Read the Say this box, close the guide, and answer in your own words. You do not need to memorize the exact sentence.
